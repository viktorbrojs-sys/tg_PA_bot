## Что уже сделано

Полная история — в `CHANGELOG.md`. Кратко, по слоям:

**Архитектура** (см. `README.md` → «Структура проекта»):
`bot/{main,config,storage,handlers}.py` + `bot/services/*` (бизнес-логика,
без Telegram) + `bot/integrations/{llm_client,google_calendar,weather_client}.py`
(абстракции с no-op fallback) + `bot/scheduler/jobs.py` (APScheduler).
Хендлеры тонкие — вся логика в `services/`, тестируется без
python-telegram-bot.

**Функционал:**
- Полный список задач (`/list`, `/list N`), разбитый на несколько сообщений
  при превышении лимита Telegram
- ИИ-классификация текста по разделам (`## Раздел` в markdown), DeepSeek с
  fallback на `Входящие` без ключа
- `/plan <текст>` — разбивка сообщения на несколько задач
- `/search <запрос>` — grep-поиск по всему файлу + краткий ответ от LLM
- `/done N` — с таймстемпом выполнения (`✅ ГГГГ-ММ-ДД ЧЧ:ММ`)
- `/review` — еженедельный обзор выполненного за 7 дней (+ по расписанию)
- **`/deadline N ГГГГ-ММ-ДД`** — поставить/убрать дедлайн задаче (необязательно, не у каждой задачи); хранится как `[due:: ГГГГ-ММ-ДД]`
- **`/priority N <уровень>`** — приоритет 0-5 (FYI/Критический/Высокий/Средний/Низкий/План) — числом или словом; хранится числом (`[priority:: N]`) для правильной сортировки в Dataview; утренний дайджест выбирает «главную задачу» с учётом приоритета
- **`/setcategory N <раздел>`** — вручную переопределить раздел задачи (хранится как `[category:: Раздел]`, дублируя `## Раздел`-заголовок)
- Утренний дайджест по расписанию (открытые задачи, просроченные по тегу
  `[due:: ГГГГ-ММ-ДД]`, **погода на сегодня**, **встречи из Google Calendar**,
  главная задача дня) — без пробок
- Вечерняя рефлексия по расписанию (свободный текст → отметка выполненных +
  явный список «переносится на завтра», информационно, без модели «дня»)
- **Google Calendar (read-only)**: встречи в дайджесте + подготовка к
  встрече за N минут (по умолчанию 30) — тема/время/место/участники + что
  нашлось по теме через `/search`. Одноразовая настройка через
  `scripts/google_calendar_auth.py` (device flow, без redirect URI)
- **Погода (Open-Meteo, бесплатно, без ключа)**: описание, диапазон
  температур, подсказка про зонт при вероятности осадков ≥40% — нужны
  только координаты (`WEATHER_LATITUDE`/`WEATHER_LONGITUDE`)
- `/search`, `/done`, `/plan` без параметра — бот спрашивает значение и берёт
  следующее сообщение как аргумент (`PendingCommandState`)
- Меню команд в Telegram (`setMyCommands`)
- Деплой: systemd (Linux) и Планировщик заданий (Windows) — готовы полностью

**Тесты:** 160, все проходят. `ruff check .` и `mypy` — чисто. CI зелёный.

## Gmail-интеграция — в работе (пошагово, см. чеклист)

Решено с пользователем:
- Только чтение (`gmail.readonly`), бот никогда не отправляет/не удаляет/не
  меняет почту
- **1.** Векторное хранилище для писем — **копия `VaultIndex` в
  `mail_index.py`**, не общий класс (риск регрессии в уже рабочем/протестированном
  `vault_index.py` — ноль; рефакторинг в общий `VectorStore` отложен до
  момента, когда паттерн устоится на практике)
- **2.** Retention индекса писем — **180 дней с автопрунингом**, конфигурируемо
  (`MAIL_INDEX_RETENTION_DAYS`, дефолт 180). Прунинг — после каждого прогона
  индексатора
- **3.** Индексировать **весь inbox** (не только конкретные лейблы/непрочитанные).
  Меры против шума от рассылок: (а) первая индексация — только письма за
  последние 180 дней (совпадает с retention), а не вся история ящика; (б)
  `SPAM`/`TRASH` исключены из запроса к Gmail API; (в) лейблы Gmail
  сохраняются в `MailMessage.labels` — если поиск окажется шумным, можно
  будет отфильтровать `CATEGORY_PROMOTIONS`/`CATEGORY_UPDATES` без
  переиндексации, просто на этапе запроса к уже собранному индексу
- **4.** `/reindex_mail` — **отдельная команда** от `/reindex` (тот остаётся
  только для vault)
- Как и с Second Brain: пока идёт реализация — README/USER_GUIDE/CHANGELOG
  не трогаем, актуализируем всё разом в конце

Полный декомпозированный план (блоки A→F) обсуждён в чате 22 сентября 2026 —
если план потерян, там же есть техническое обоснование каждого решения
(например, почему loopback-flow с отдельным OAuth-клиентом для Gmail, а не
device-flow, как у Calendar: Google не разрешает Gmail-scope в «TVs and
Limited Input devices»).

## Как продолжать работу (важно для новой сессии)

1. **Клонировать репозиторий** `github.com/viktorbrojs-sys/tg_PA_bot`,
   работать в отдельной директории (не трогать `.git`).
2. **Прогонять перед каждым коммитом:**
   ```bash
   python -m pytest -q
   python -m ruff check .
   python -m mypy
   ```
   Все три должны быть чистыми — это принцип проекта с самого начала.
3. **Пуш в GitHub** — нужен персональный токен доступа (fine-grained PAT) с
   правом **Contents: Read and write** на этот репозиторий; пользователь
   присылает его в чате при просьбе. Использовать разово: клонировать с
   токеном во временную директорию → синхронизировать файлы → закоммитить →
   запушить → **сразу удалить локальный клон с токеном**. Никогда не
   выводить токен целиком в лог/вывод команд (маскировать через `sed`).
4. **Стиль работы, которого придерживались всю дорогу:**
   - Сервисный слой (`services/`) не знает про Telegram — тестируется
     отдельно
   - У всех внешних интеграций (LLM, будущий календарь) — абстракция +
     fallback без ключа/настройки, чтобы бот не ломался без опциональных
     настроек
   - Инжектируемые часы (`now`/`today` как параметр) для тестируемости
     таймингов
   - Каждая фича — тесты + обновление `CHANGELOG.md` и `README.md`
     (а для пользовательского поведения — и `USER_GUIDE.md`) в этом же коммите
5. **Русский язык** — весь пользовательский текст (сообщения бота, докстринги
   на функциональности для пользователя) на русском; код/комментарии для
   разработчика — на английском (уже сложившийся стиль в репозитории).
